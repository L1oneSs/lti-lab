# Подготовка к защите лабораторной Moodle LTI

Основание: раздел 16 на странице 17 `docs/Moodle_LTI_Three_Tasks_Lab.pdf`. Ниже ответы на все шесть вопросов PDF, объяснение собственного варианта и план демонстрации. Тесты с имитацией платформы не заменяют проверку оценок в настоящем Moodle.

## 1. Откуда взят userId?

Из проверенного LTI-запуска Moodle: `context.idToken.user.id`. Подпись и параметры сообщения запуска проверяет библиотека ltijs. Приложение дополнительно сверяет issuer, Client ID и Deployment ID, наличие пользователя, курса и ресурса. Последующие обращения API получают тот же контекст через серверную сессию.

Браузер не выбирает пользователя для оценки. В JSON отправки разрешены только `answers` и `requestId`: попытка добавить `userId` отклоняется с HTTP 400. При вызове AGS сервер использует `token.user.id`, а не значение из формы. Этот идентификатор не обязательно совпадает с логином Moodle.

Короткий ответ: «userId приходит из подписанного и проверенного запуска Moodle. Подменить его через форму нельзя».

Где показать: `src/tool.mjs`, функции `validateLaunch`, `identityKey`, обработчик `/api/submit`.

## 2. Почему браузер не должен присылать итоговый балл?

Пользователь контролирует браузер и может изменить JavaScript или отправить собственный HTTP-запрос. Если сервер доверяет присланному баллу, пользователь может поставить себе любую оценку.

Поэтому браузер передаёт ответы, а серверная функция `grade` проверяет структуру и сравнивает ответы с эталонами. Правильные ответы хранятся в `src/grading.mjs`; API выдаёт только ID, формулировки и веса заданий. Лишнее поле `scoreGiven` приводит к HTTP 400.

Наши задания: `q1` — `a`, 3 балла; `q2` — `img`, 3 балла; `q3` — `ol`, 4 балла. Сумма — 10. `trim().toLowerCase()` убирает крайние пробелы и игнорирует регистр. Например, ` IMG ` принимается, `<img>` не принимается. Пустая или неверная строка даёт 0; неправильная структура, нестроковый ответ, лишний ключ или строка длиннее 200 символов дают HTTP 400 без отправки оценки.

Короткий ответ: «Браузеру нельзя доверять расчёт: его запрос можно изменить. Балл вычисляется сервером по ответам».

Где показать: `src/grading.mjs`, `test/grading.test.mjs`, публичные поля `tasks` в `/api/session`.

## 3. Что такое line item?

В AGS line item — объект оцениваемого элемента, соответствующий колонке журнала. Это не строка конкретного студента. Конкретный студент выбирается через `userId` в сообщении Score.

Адрес существующего line item берётся из проверенного запуска: `token.services.assignmentAndGrades.lineItemId`. Приложение вызывает `context.grading.submitScore` с этим адресом. Оно не создаёт новую колонку для каждой попытки и не собирает адрес сервиса вручную.

Сообщение включает `userId`, `scoreGiven`, `scoreMaximum`, `activityProgress: 'Completed'`, `gradingProgress: 'FullyGraded'` и серверный `timestamp`. Библиотека получает OAuth access token и отправляет оценку Moodle. Максимум приложения и элемента Moodle должен быть 10; при другом максимуме Moodle может масштабировать результат.

Короткий ответ: «line item определяет, в какую колонку записать результат, а userId — какому студенту».

Где показать: вызов `submitScore` в `src/tool.mjs` и колонку элемента в журнале Moodle.

## 4. Почему преподаватель не отправляет себе оценку?

Это правило учебного каркаса, а не универсальное требование стандарта LTI. Преподаватель просматривает задания; выполнять упражнение с записью оценки может пользователь с ролью Learner из проверенного запуска.

Интерфейс отключает поля и кнопку. Сервер отдельно проверяет роль для POST-запросов и возвращает HTTP 403, если Learner отсутствует. Поэтому включение кнопки через DevTools не даст преподавателю право отправить оценку.

Короткий ответ: «Такова политика лабораторной: преподаватель смотрит, студент выполняет. Запрет действует и в интерфейсе, и на сервере».

Где показать: проверку `token.user.roles.includes(LEARNER)` и уже полученный экран «роль: просмотр». В каркасе проверяется наличие Learner; не следует утверждать, что он отдельно запрещает любой запуск с одновременно присутствующими Learner и Instructor.

## 5. Чем новая попытка отличается от повтора отправки?

Новая попытка — новые ответы и новый расчёт. Она начинается через `/api/new-attempt` после подтверждения доставки текущей оценки: текущая попытка переносится в историю, интерфейс разрешает следующий ответ. Балл последней завершённой попытки заменяет предыдущий, даже если он ниже.

Повтор отправки — доставка той же сохранённой попытки с тем же `requestId` и теми же ответами. После сбоя AGS попытка остаётся `pending`, `sentAt` пуст; новая попытка блокируется до подтверждения. Сервер использует сохранённый результат. Если доставка уже подтверждена, повтор текущего запроса возвращает прежний результат без нового вызова AGS.

Сбой может быть неоднозначным: Moodle уже принял оценку, а ответ потерялся. Поэтому здесь нет обещания exactly-once. Одна учебная попытка может доставляться повторно; для каждого вызова AGS сервер сохраняет строго возрастающий timestamp. Защита от повторов относится к текущей попытке, не к произвольным старым запросам за всё время.

Короткий ответ: «Новая попытка меняет учебный результат, повтор лишь доставляет прежний. pending нельзя обойти созданием следующей попытки».

Где показать: `/api/new-attempt`, `/api/submit`, `requestId`, `status`, `sentAt`, `lastScoreTimestamp`.

## 6. Что исчезнет и что сохранится после перезапуска Node.js?

| Где хранится | Данные | После перезапуска Node.js |
|---|---|---|
| Память процесса | Сессии интерфейса на 45 минут, одноразовые билеты перехода, очередь блокировок | Исчезнут; элемент нужно открыть из Moodle заново |
| MongoDB | Регистрация платформы, ключи и данные библиотеки LTI | Сохранятся, если база и её Docker-том сохранены |
| Папка `data` | Текущая попытка, ответы, результат, история и время доставки | Сохранятся, если папка не удалена |
| Moodle | Принятая оценка в журнале | Сохранится независимо от процесса приложения |

Cookie может остаться в браузере, но после перезапуска ему уже не соответствует сессия в памяти. Новый запуск того же пользователя и ресурса восстановит историю из `data`. Приложение рассчитано на один процесс Node.js: очередь блокировок не защищает от гонок между несколькими процессами.

Остановка Codespace сохраняет рабочее окружение, но требует нового запуска приложения; удаление или пересоздание окружения может потерять базу и файлы. Нельзя считать эти операции просто перезапуском Node.js.

Короткий ответ: «Пропадут временные сессии; история, ключи и оценка останутся при сохранённых хранилищах».

## Общий поток

1. Пользователь открывает элемент курса Moodle.
2. Moodle запускает приложение по LTI 1.3; ltijs проверяет запуск, сервер сверяет регистрацию.
3. Сервер создаёт временную сессию, получает идентичность, роль и контекст ресурса.
4. Браузер получает три вопроса без эталонов и отправляет `answers` + `requestId` с CSRF-токеном.
5. Сервер проверяет роль, источник, CSRF и структуру данных, рассчитывает балл и сохраняет попытку.
6. Сервер через ltijs отправляет Score в AGS существующего line item.
7. После подтверждения помечает попытку `sent`; Moodle показывает оценку в своей колонке.

MongoDB здесь не LRS. xAPI и LRS в лабораторной не используются. Порт 3000 обслуживает Node.js, порт 27017 — MongoDB. Публичным в Codespaces нужен только 3000; внешний HTTPS предоставляет прокси Codespaces.

## Что ещё показать на настоящем Moodle

Запуск преподавателя подтверждён скриншотом пользователя. Следующие результаты пока не подтверждены:

| Проверка | Ожидаемый результат |
|---|---|
| Студент А: `x / x / x` | 0/10 и 0 в его строке журнала |
| Новая попытка А: `a / x / ol` | 7/10 и 7 вместо 0 в той же колонке |
| Новая попытка А: `a / img / ol` | 10/10 и 10 вместо 7 |
| Обновление окна / повтор текущего запроса | Та же попытка, без новой колонки |
| Студент Б: `x / x / x` | У Б 0, у А остаётся 10; история А не видна Б |
| `/api/session` без LTI-сессии | HTTP 401 |
| POST преподавателя | HTTP 403, оценка не меняется |
| POST студента без CSRF | HTTP 403, оценка не меняется |
| Лишний `userId` или `scoreGiven` | HTTP 400, оценка не меняется |

Повтор nonce и сбой AGS проверяются интеграционным тестом на имитации. Общий Moodle ради имитации сбоя выключать не нужно. Снимки журнала должны подтверждать студента, элемент и фактический балл; других пользователей и идентификаторы сессий нужно скрыть.

## Индивидуальная демонстрация изменения правила

PDF требует уметь изменить одно правило. Пример для объяснения: разрешить ввод `<img>` наряду с `img`. Для этого серверная нормализация должна снимать только одну пару внешних угловых скобок у корректного имени тега; атрибуты по-прежнему запрещены. Затем нужно изменить подсказку формы и тест, который сейчас ожидает отказ для `<img>`, добавить проверки допустимой формы и запрещённых атрибутов, выполнить `npm test`, перезапустить сервер и показать результат.

Это план демонстрации, не выполненное изменение. Основной сдаваемый вариант продолжает требовать имена тегов без скобок. Не менять правила между фиксацией контрольных результатов А/Б и сдачей отчёта без обновления описания.
